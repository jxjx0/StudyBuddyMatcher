STUDY BUDDY MATCHING: SCORE CALCULATION AND JAVA CLASS FLOW
============================================================

WHAT THE DISPLAYED PERCENT MEANS
--------------------------------
The "N% match" shown on the Discover page is one overall score combining all
enabled criteria. It is not the raw percentage for any single criterion.

For every enabled criterion:

    contribution = criterion compatibility (0.0 to 1.0) x criterion weight

The engine then normalizes by the total weight of the enabled criteria:

    overall score = 100 x sum(contributions) / sum(enabled weights)

The default balanced configuration enables five criteria at 20% each. If
availability compatibility is 50%, availability contributes:

    0.50 x 20 = 10 percentage points

If every other criterion scores zero, the overall score is 10%. If the other
criteria have positive scores, their contributions are added too.

If some criteria are disabled, their weights are omitted and the remaining
enabled criteria are normalized to the sum of their weights. The admin
configuration service validates that enabled weights total 100 when settings
are saved.

PER-CRITERION COMPATIBILITY RULES
---------------------------------

Course:
  Uses the searcher's distinct course codes from coursesForStudying. If that
  list is empty, it falls back to the searcher's currentCourses. The candidate
  is compared using the union of their coursesForStudying and currentCourses.
  Score = number of searcher's wanted codes found on the candidate / number of
  searcher's wanted codes. Course codes are trimmed and compared
  case-insensitively. If the searcher has no usable course codes, score is 0.

Availability:
  The engine merges overlapping or touching time slots for each student first,
  so duplicate availability does not count more than once. Slots only overlap
  when their days match (case-insensitively) and their time ranges intersect.
  The engine sums the shared minutes across the week.

  Score = shared availability minutes / the larger student's total available
  minutes across the week.

  Example: Monday 18:00-20:00 versus Monday 18:00-19:00 has 60 shared minutes.
  The larger schedule is 120 minutes, so availability compatibility is 50%.
  With a 20% availability weight, that contributes 10 percentage points to the
  weighted score. If the only slots are on different days, shared minutes and
  availability compatibility are zero.

Study mode:
  IN_PERSON matches IN_PERSON; ONLINE matches ONLINE. EITHER matches either
  specific mode. A missing (null) mode is also treated as compatible. The
  compatibility score is either 100% or 0%.

Study goal:
  Uses the distinct goals selected by both students.
  Score = number of shared goals / number of goals in the union of both sets.
  With no goals on either side or no shared goals, the score is 0%.

Group size:
  ONE_TO_ONE matches ONE_TO_ONE; SMALL_GROUP matches SMALL_GROUP. EITHER matches
  either specific preference. A missing (null) preference is treated as
  compatible. The compatibility score is either 100% or 0%.

JAVA CLASS FLOW
---------------

1. MatchingController.findMatches handles
   POST /api/matching/students/{studentId}/search. It asks StudentClient for the
   searcher's profile and passes that profile and any search filters to
   MatchingEngine.

2. StudentClient calls user-service for the profile or candidate list.
   StudentDto contains the profile fields used for scoring, including courses,
   weeklyAvailability, studyGoals, meetingMode and groupSizePreference.

3. MatchingConfigurationService loads the saved strategy and enabled criterion
   weights from the matching configuration tables at startup. It also serves
   the admin configuration API and applies validated changes.

4. MatchingEngine.findMatches retrieves the current weights, asks StudentClient
   for candidates and excludes the searcher, inactive students and candidates
   that fail the requested filters. Filters restrict which candidates are
   scored; they are not extra scoring criteria.

5. MatchingEngine.scoreComponents calls the criterion methods:
   scoreCourseMatch, scoreAvailabilityOverlap, scoreStudyModeCompat,
   scoreStudyGoalOverlap and scoreGroupSizeCompat. The result is a value from
   0.0 to 1.0 for each criterion.

6. MatchingEngine.resolveWeights applies the configured MatchingStrategy.
   BalancedMatchingStrategy gives equal shares to all enabled criteria.
   AvailabilityFirstMatchingStrategy and CourseFirstMatchingStrategy enforce
   that their named criterion has the highest weight; the administrator's
   valid weights otherwise remain unchanged.

7. MatchingEngine.weightedScore combines the criterion values and weights.
   Results are sorted from highest score to lowest. The engine rounds the
   overall score to one decimal place and creates a MatchResult for each
   candidate.

8. MatchResult serializes the candidate, overall score and matchedCriteria
   names into the API response. matchedCriteria is a list of labels for enabled
   criteria with a score greater than zero; it does not contain individual
   criterion percentages or weighted contributions.

9. The frontend DiscoverPage calls the matching endpoint through useMatching.
   It rounds the API score to a whole number and displays it as "N% match".
   It displays matchedCriteria as criterion chips. Thus the visible percentage
   may differ by less than one point from the one-decimal backend score because
   of frontend rounding.
